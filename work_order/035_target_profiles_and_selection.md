## 目标与范围

在规划前向 Agent 提供目标能力与必要限制，并为导出提供可检查的 profile。Unity 与 Minecraft 保持首批目标；比较后续游戏的场景导入入口，确定是否选择一个新目标。不同平台保留各自输出，WIR 不压缩成所有平台的最低公共能力。

## 工作项

- [ ] 定义目标名称、精确版本、适配器版本、单位/坐标/量化、支持的任务与几何/资产、材料、碰撞、必要组件及资源上限。
- [ ] 定义必须保留的源需求、可接受近似和明确不支持的能力；缺少必要 profile 字段或违反硬性目标限制时在规划/导出前诊断。
- [ ] 建立 Unity 与 Minecraft 首批 profile，区分源端声明、文件结构检查、目标实际加载和漫游证据等级。
- [ ] 明确多目标约束如何进入 A：硬需求必须满足，允许不同派生表示；近似不能静默修改 WIR 或删除必需对象。
- [ ] 使用官方工具/SDK 文档及必要的工具作者资料比较候选游戏，记录访问日期、版本、导入格式、资产约束、场景必要组件、验证环境与复用成本。
- [ ] 记录下一平台选择依据和实际使用需求；偏好未确定时提交比较结果供用户选择，不擅自承诺所有平台。
- [ ] 将纯格式导入、可用场景交付与线上投稿分开；选型只要求场景搭建和本地验证，不包含玩法或自动投稿。

## 验收标准

- profile 可被 Schema 校验，未知版本或必要能力缺失产生明确错误，不能仅凭平台名宣称兼容。
- 自然/建筑/混合样例能列出各目标的约束及损失规则；必要构件缺失使导出失败，可接受近似逐对象可追溯。
- 两个平台的 profile 引用真实可用处理器和独立证据等级，不将旧规则场景证据算成新任务能力通过。
- 后续平台比较有可核对来源、范围和理由；尚未选择或环境不足时记录待定，037 不自行启动。
- 本工单完成配置契约和选型记录，不代表适配器或目标场景已完成。
