# 当前项目基线：Agent 场景搭建

日期：2026-10-10。状态：用户确认的产品定位与当前实施路线；本文件不新增运行契约或宣称后续功能已经实现。分支职责见 [027](../work_order/027_branch_role_alignment.md)，后续任务见 [028](../work_order/028_followup_work_order_planning.md)。

## 目的与范围

玩家和创作者希望制作自己的游戏地图与场景，但手工搭建耗时、需要资产与设计技能，效果也难以稳定。本项目让 Agent 主导场景规划与设计，将创作描述转成可验证的中间计划、世界源数据和目标平台产物。

场景包括地形、水体、植被、岩石、道路、建筑、室内与其他摆放资产；自然、建筑和混合场景都是产品目标，不能把建筑作为每次生成的必需对象。专业编辑器和游戏地图工具属于产物消费端，不要求每个平台共享相同的几何或编辑能力。

产品闭环目标是“描述 → 构建 → 查看 → 反馈修改 → 保存修订 → 导出”。这里的地图是可搭建、可使用的场景；游戏规则、任务系统、解谜、胜负条件、自动线上投稿不在当前范围。IFC 保留为独立可选的专业扩展，不作为游戏场景闭环的前置条件。

## 当前实现与证据

本地 `main` 是原 Agent 分支；`codex/local-validation` 是原规则主线。更名没有迁移旧规则路线的所有能力，也没有同步远端。`main` 保留部分旧代码供复用与回归，默认产品入口仍为 Agent 流水线。

| 层 | 已有行为 | 适用边界 |
|---|---|---|
| 规划 | 固定 A → 并行 B/C → D → 每场地 E → F；严格 JSON、预算、并发、有限返工与回放 | 0.1.0 建筑场地导向，通用任务图未实现 |
| 编译与源世界 | 本地验证、几何编译、WIR 事务存档与 worldpkg | 整米轴对齐盒体、格状地形、静态水、有限材质 |
| 导出 | Unity 静态 GLB、Minecraft Sponge v3 schematic 与坐标/对象映射及损失报告 | 未新增自动 Unity 导入/碰撞体/NavMesh；Minecraft 需目标工具放置 |
| 交互 | 网页测试台及 Windows 桌面壳；旋转、剖切、拾取、诊断、历史回放与下载 | 只读预览，没有用户编辑、撤销或增量再生成 |
| 验证 | 023—026 的人工响应闭环、回放及应用验收记录 | 真实模型质量、稳定性、费用及其目标场景实走仍待 024 |

当前世界坐标为右手系 X 东、Y 北、Z 上，长度 m；Agent 几何没有自由旋转。区域边长为 32—512 m、16 的整数倍，这是输入限制，不能视为任意场景规模与质量的保证。准确字段与规则见 [0.1.0 契约](contracts/api-agents-v0.1.md)。

当前 D 对场地支撑、干燥及道路连接有建筑导向要求，E 检查入口与逐层通路。因此“森林溪流、无建筑也无道路”尚不是已验收能力。整格通路验证也不能证明目标引擎的实际角色能行走。旧路线的城堡、船只和目标样件证据必须保留原版本、输入及环境，不能直接用于 Agent 产物。

当前请求哈希带全局描述，编译身份也随接受计划变化；已有修订库不等于已有同一世界上的持续反馈编辑。稳定世界/对象身份和局部依赖需由 032/033 建立。

## 后续架构与粒度

以下为已拆工单的设计目标，尚未实施。主链仍是 Agent 产出候选计划、本地程序校验和编译；从固定阶段升级为有显式能力、输入、输出和依赖的场景任务。

| 角色/层 | 目标职责 |
|---|---|
| A 需求与任务建议 | 解析场景目标、必需/可选对象与约束，提出任务图；由监督器检查能力、依赖、预算和必需项覆盖 |
| B 基底 | 地形、水体与场景基础；按需求和目标能力执行 |
| C 对象与资产 | 建筑、植被、岩石及其他对象/资产清单、配方和资源来源 |
| D 空间布局 | 对象、区域、实例组的布局与空间关系；约束按对象能力适用 |
| E 专项设计 | 根据任务类型执行建筑、自然资产、实例组等设计；每种任务有明确输出契约和校验器 |
| F 场景审查 | 检查整体需求覆盖、空间协调及质量，提出受限作用域返工；不能删掉用户必需项或降低硬约束 |
| 本地监督与数据层 | 验证任务图，调度、预算、失败分类、依赖失效、接受事务与稳定修订 |
| 目标层 | 规划前读取 target profile，导出时明确映射、量化、遗漏与目标验证状态 |

阶段是否执行由任务能力和依赖决定。例如无建筑的森林不启动建筑设计任务，但仍可能需要地形、树石清单、布局与实例分布；不能仅凭 A 写了“自然景观”就跳过 C/D。必需对象没有可用能力时明确拒绝或请求需求调整，不能静默跳过后宣称完成。

用户修改以世界修订和选中对象为上下文：记录实际读取依赖与写入范围，保留未受影响对象和锁，只使相关任务与边界验证失效。目标导出设置变化只更新派生产物；场景上下文变更必须传播至真实依赖任务。撤销/重做通过已有修订恢复，不重新付费生成。后端修改服务先落地，工作台与完整手工编辑器复用同一套接口。

Unity 与 Minecraft 是首批目标；下一平台在官方能力、格式、环境与使用场景比较后确定。目标约束应进入规划前置条件。文件生成、目标加载、实际观感/通行、线上投稿分别验收，不能由前一层推断后一层通过。
