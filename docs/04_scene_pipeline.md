# 场景驱动生成流水线：现状差异与重构方案

## 当前适用说明（2026-10-10）

下文诊断的是当时的旧规则控制面。当前 main 已通过 023 将固定 A—F 规划交给 API 模型，见 [05](05_api_agent_pipeline.md)；下一阶段按通用任务、能力和依赖构建自然/建筑/混合场景，见 [项目基线](00_project_baseline.md)。旧文中的零调用默认、模板复用策略及阶段状态不代表当前实现。历史文字中的删改工单建议不作为执行规则；编号、记录保留按 [AGENTS](../AGENTS.md) 执行。

## 2026-09-26 原始记录（保留历史）


版本：0.1（设计文档，未实现）。日期：2026-09-26。作者：root。

本文回答一个具体问题：**用户设想的 A—F 智能体流水线，与当前实现差在哪里，怎样用最小代价落地。**
结论先行：**差异集中在"控制面"（规划与设计），而不在"数据面"（WIR、校验、存档、导出、证据）。**
数据面已经过目标平台验证，正是 A—F 的终点所需要的东西，因此**建议原地重构控制面，不在父目录重开项目**（理由见第 5 节）。

## 1. 用户设想的流水线（作为需求基线）

| 步骤 | 角色 | 职责 |
|---|---|---|
| A | 场景总控 | 接收具体场景（魔法城邦 / 现代大都市 / 工业园 / 港口…），分解任务 |
| B | 地形分析 | 判断该背景需要的地形（河网、丘陵、起伏、海岸、平地） |
| C | 风物分析 | 判断该背景必须出现的建筑与风物（城堡、城墙、公会、教堂、旅馆 / 枢纽、摩天楼、医院、学校 / 厂房 / 码头、货轮…） |
| D | 分区与选址 | 把地图切成大小不一的区块，安排建筑粗位置，给出每栋的最大占地；先建河流、轨道、道路骨架 |
| E | 单栋设计 | 每栋建筑按背景、占地上限、类型自行规划外形、层数、各层内容、楼梯（可用建筑规划 skill） |
| F | 装配 | 收集所有 E 的结果，与 D 的整体规划合并，导出大 WIR |
| — | 导出 | Unity / Minecraft / 本地查看器 |

这与 [正式方案](03_formal_proposal.md) §4.2 的"区域骨架 → 生态与用地 → 路网与分区 → 地块与建筑体量 → 楼层与房间 → 家具与装饰 → 几何编译"是同一件事的两种表述：**A—F 是角色划分，§4.2 是数据阶段划分。**

## 2. 现状（可核对的事实）

当前 512 m 城邦生成器的控制面**只有一次模型调用**，之后全部由固定分支和硬编码表决定：

| 设想中的阶段 | 现状 | 证据 |
|---|---|---|
| A 场景简报 | 只有自由文本 `source_prompt`，模型被限制只能回 6 个字段：`scenario`、`building_count`、`interior_count`、`layout_profile`、`lock_stair_void` | `src/world_builder/generation/model.py` 的 `OUTPUT_FIELDS` |
| B 地形分析 | 没有分析。地形是解析函数 `height()`（一个正弦 + 按 x 渐变），河是**城市正中 8 m 宽的直条**，没有河网、丘陵、海岸、坡度统计 | `planner.height()`、`stage == "terrain"` 分支 |
| C 风物目录 | 没有目录。功能来自固定元组 `PROGRAMMES`，分区功能来自两张硬编码表 `DISTRICT_PLAN` / `MODERN_DISTRICT_PLAN`；"背景"只有两个样式常量 | 同上 |
| D 分区与选址 | 只有 3 条南北向条带（固定 `x_pitch=42/44`、`y_pitch=52/56`），地块固定 32×28 m，竖向净空固定，没有区块大小差异、没有归属层、没有非正交路网 | `stage == "network"/"parcels"` |
| E 单栋设计 | 没有单栋产物。每栋的形态是"按种子取宽度/进深/层数 + 按功能查表"，平面只有一种："楼梯井以东切两间房 + 一道隔墙"，家具按用途查表 | `stage == "buildings"/"interiors"` |
| F 装配 | 没有独立装配阶段。五个阶段顺序提交，冲突只在阶段内用"候选 + 有限修复"处理 | `pipeline.py`、`repair.py` |

反过来，**下游全部是真的、且经过验证**：WIR 0.1 合同与校验（005）、SQLite 修订库与分支头、ZIP64 世界包、Minecraft 1.21.11 目标世界实贴（009）、Unity 6000.3.24f1 导入与连续通行（008）、预登记批次与证据纪律（各类 `report.json` + `docs/check_project_docs.py`）。

**一句话总结差异**：现在的项目是一个**用固定模板直接画出 512 m 城邦**的生成器，加上一套成熟的数据面；用户要的是一个**由场景驱动、分层委派、每栋建筑单独设计**的生成系统。缺的是中间那层"规划"，不是底座。

## 3. 重构方案：把控制面拆成 A—F 六个可验收阶段

每个阶段都是**同一个形状**：输入契约 → 规划产物（JSON，带单位与上限）→ 独立校验规则 → 预登记批次 → 失败按作用域回馈上一层。

```text
简报(A) ──> 地形方案(B) ──┐
                          ├──> 区块与选址(D) ──> 单栋设计(E)×N ──> 装配(F) ──> WIR ──> 目标导出
风物目录(C) ──────────────┘
```

### 3.1 每个阶段的双实现（可落地的关键）

每个阶段都有**两份实现，共用一份契约**：

- **离线确定性实现（默认）**：规则/表驱动的参考实现，零模型调用，可跑批次、可回归、可复现。今天的 `DISTRICT_PLAN`、`PROGRAMME_*`、`_building_shell` 正好就是 D、C、E 的第一版参考实现，直接继承。
- **模型实现（可选）**：按同一 JSON 契约产出同样的规划产物；模型只填字段，不写代码、不写几何。

这样做的直接好处：**流水线不因"要不要接云模型、额度多少"而停摆**，真实模型是同一接口的升级项，而不是前置条件。

### 3.2 硬性原则

- **P1 模型只产出计划与数值，不产出几何。** 方块、三角面、墙体仍由程序化生成器 + 校验器产生。语言模型写体素无法验证，会直接摧毁现有证据体系。
- **P2 阶段产物是版本化资产。** 每次接受的结果连同内容哈希、提供者、种子一起存档，可离线回放（复用 006 已有的"已接受响应作为 SHA-256 资源"机制）。
- **P3 失败按作用域回馈。** E 失败 → 换包络/重试该栋；D 失败 → 重划该街区；只有选址在给定地形下不可行，才回到 B。绝不因为一栋楼画不下就整城重跑。
- **P4 成本要有上限。** "每栋一个子智能体"不等于"每栋一次模型调用"。默认路径是**设计模板 × 站点参数**：按"类型 × 背景 × 尺度档"生成设计模板（skill pack），再按每栋的包络实例化；只有地标（城堡、教堂、市政厅、车站、码头）值得单独调用。一座 80 栋的城市默认 0—8 次模型调用。
- **P5 背景是数据不是代码。** 新增"港口/工业园/现代都市"应当是新增一个背景包目录（地形偏好 + 风物目录 + 设计模板 + 材质词汇），而不是改生成器分支。
- **P6 每个阶段独立验收。** 不只看"几何合法"，还要看"是否满足简报"：必须出现的风物是否出现、数量与邻近关系是否满足、地形是否符合背景偏好。这些断言本身要可核对。

### 3.3 阶段契约（字段级概要）

| 阶段 | 输入 | 输出（关键字段） | 独立校验 |
|---|---|---|---|
| A 场景简报 013 | 自然语言 + 用户约束 | `setting`、`era`、`scale_m`、`required_landmarks[{type,count,priority}]`、`mood`、`targets`、`budget` | 字段完备、数量/尺度在上限内、必现风物非空 |
| B 地形方案 014 | 简报 + 种子 | `relief`（地貌单元与控制点）、`hydrography`（河网/海岸中心线与宽度、水流等级）、`buildable`（适宜度场与保留区） | 水系连通且出图边界明确、坡度/高差在简报范围、保留区不与被占区冲突 |
| C 风物目录 015 | 简报 | `catalogue[{type, role, required, count_range, footprint_m2_range, height_m_range, adjacency[], needs_water/needs_road}]` | 必现风物齐全、尺寸与背景合理、邻近关系无环冲突 |
| D 区块与选址 016 | 地形方案 + 目录 | `domains[]`（归属/领地，可含多个区块）、`blocks[]`（大小不一）、`network`（道路/轨道/桥/码头骨架）、`sites[{building_type, block, envelope{max_footprint_m2,max_height_m,access}}]` | 区块面积与目录一致、道路连通、每栋有可用包络、地块不重叠、包络不压水系保留区 |
| E 单栋设计 017 | 单个 site + 目录条目 + 背景包 | `design{outline, storeys, storey_rooms[], stair, entry, roof, materials, furniture[]}` | 外形在包络内、房间不重叠且连通、楼梯落地、入口接路、屋顶与风格一致 |
| F 装配 018 | 地形方案 + 区块 + 全部 design | `WIR 修订 + 源端检查 + 世界包` | 跨阶段不变量（重叠、越界、可达、支撑）、失败作用域正确回馈 |

阶段产物的字段名在 013—018 工单里逐条冻结；本文只固定**形状**，避免设计文档写成"已实现能力"。

## 5. 为什么建议原地重构，而不是在父目录重开

1. **最难、最贵的部分已经做完**：WIR 合同、校验器、修订库、世界包、两个目标平台的适配器与实机验证、以及预登记批次+证据的纪律。A—F 的 F 与导出步骤直接复用这些，重开项目要全部重做并重新验证。
2. **要改的是"谁在规划"，不是"数据长什么样"**：把控制面拆成 013—018，数据面一行不改，Minecraft/Unity 的既有证据继续有效。
3. **重开会丢掉目标世界的可比性**：当前世界里已有两座 city.7 城邦，是唯一"已贴进真实游戏"的基线。重开项目意味着连比照对象都没有。
4. **重开也不省事**：新的工单系统仍需要同样的版本/证据/边界规则（`AGENTS.md`），以及同样的适配器——只是把它们再写一遍。
5. **风险可控的中间路线已经存在**：013—018 全部是 **planned**、互不阻塞，可以先做 013/014/015 这三个纯离线阶段，确认"背景→地形+风物"这条链是否真的产出你想要的东西，再决定要不要投入模型与人力做 E 的 skill 库。若中途发现方向不对，删除新增工单与 `docs/04`，旧项目状态完好无损。

**唯一值得重开的信号**：如果要换语言/运行时（例如整体改用 C#/Rust 或换掉 WIR 0.1 的形状）。当前没有任何证据要求这么做。

## 6. 落地顺序（建议）

1. **013 + 015**：先把"简报 → 风物目录"打通，并落两个背景包（`arcane_medieval`、`modern_grid`），因为它们决定后面所有阶段的输入；纯数据、可离线、可立刻验收。
2. **014**：把地形从"解析函数 + 直河"升级为"控制点 + 排水 + 可建设适宜度"，并让 016 能在不改地形的前提下完成选址。
3. **016**：区块大小不一、归属层（若干区块同属一个城堡/城邦）、非正交路网——这也是用户已裁定纳入 006 的宏观划分与非正交路网，正式落到新流水线里。
4. **017**：先做"设计模板 × 站点实例化"（成本可控），再做地标单独设计；建筑 skill 以数据文件形式按背景扩张。
5. **018**：装配、跨阶段不变量、失败作用域回馈、预登记批次。
6. 每个阶段完成后立刻在其上跑一批"背景 → 目标平台"的端到端样例（复用 008/009 的导出与实贴流程），避免再次出现"离线很好看、进游戏不对"的偏差。

## 7. 明确不做

- 不在本阶段训练模型；不让模型直接写方块、三角面或文件操作。
- 不承诺真实地理 CRS、真实水文或工程可施工性；地形仍是"视觉与拓扑自洽"的合成地形。
- 不把"每栋一个模型调用"当作默认路径（成本与可复现性都不允许）。
- 不在 013—018 未验收前删改 001—012 的历史结论与本仓库已验收证据。
