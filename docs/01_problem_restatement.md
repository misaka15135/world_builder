# 问题重述与需求基线

日期：2026-09-21。状态：需求基线 v0.1；对应工单：001。

## 1. 问题重述

目标是构建一个由自然语言驱动的、可持续编辑的三维世界生成系统。系统将“生成一个魔法风格的城邦地区”转化为可计算的世界规格，逐层生成地形、水系、生态、道路、街区、地块、建筑、楼层、房间和室内物件，并保存各层的语义、空间关系、约束、几何参数和生成依据。

用户所说的“元形式”可定义为 **世界中间表示（World Intermediate Representation，WIR）**：独立于具体游戏引擎或导出文件的、带版本的世界源数据。它既描述“有什么、在哪里、是什么形状”，也描述“为什么这样生成、哪些条件必须满足、修改后哪些内容需要更新”。渲染网格、Minecraft 方块和 IFC 构件是根据源数据生成的不同结果。

这里的“世界模型”首先指可生成、可查询和可编辑的数字世界系统。当前目标不要求从零训练单一大模型，也不要求预测物理世界未来的视频模型。是否训练专用模型应依据原型积累的失败类型、数据和预算决定。

## 2. 已确认需求

| 编号 | 需求 | 可观察结果 |
|---|---|---|
| R01 | 接收自然语言世界描述 | 产生可检查、可修改的结构化世界规格 |
| R02 | 从宏观到微观生成 | 地形、水系、生态、聚落、建筑、室内之间有明确依赖 |
| R03 | 分阶段存储 | 中间阶段可保存、恢复、查询与继续细化 |
| R04 | 通用元表示 | 原始语义和约束不依附 Unity、Minecraft 或单一网格格式 |
| R05 | 本地轻量三维查看与修改 | 选中对象、修改属性或位置、撤销、保存并局部再生成 |
| R06 | 导出 Unity 地图 | 可导入的场景包，保留层级、对象标识和适用的碰撞/材质 |
| R07 | 导出 Minecraft 区域 | 首先验证 Java 版指定版本下的区域粘贴；独立世界目录另行验证 |
| R08 | 长期支持建筑工程三维表达 | 分阶段支持构件语义与 IFC 交换，工程设计验证另列能力 |
| R09 | 工单驱动协作 | 独立 `work_order/`、递增编号、动作记录、完成划线、工作前必读 |

用户补充确认：首个可运行版本优先支持“可编辑魔法城邦 + Unity/Minecraft”；团队与资源基线为个人或小团队、普通电脑运行，允许调用云端模型 API。

## 3. 对初步流程的必要补充

单纯“由大到小生成并保存”还需要补充以下机制。

1. **先定义规格与预算。** 面积、地形尺度、建筑数量、目标平台、精细程度和 API 预算应进入可编辑规格。未给出的参数采用明确标注的默认值。
2. **双向约束传递。** 道路宽度、地块边界、楼层高度、楼梯预留和出入口影响后续布局；若室内无法安排，必须向建筑或地块层反馈，不能仅继续添加物体。
3. **分离语义层级与空间分块。** 河流、桥梁和道路可以跨区块，不能因为文件切块而截断实体关系。
4. **按需细化。** 远处建筑先保存体量与立面；进入或选中建筑时再生成室内，避免在首帧生成整个地区的家具。
5. **显式处理修改传播。** 改河道可能影响桥梁、道路、地块和建筑；改椅子只应影响局部碰撞、通行与相关渲染缓存。
6. **验证后提交。** 每个阶段在暂存版本中运行，满足约束后成为正式世界版本；不可行时返回具体冲突。
7. **按目标报告损失。** Minecraft 的量化、Unity 的材质转换和 IFC 的语义要求不同，不承诺跨平台完全无损。

## 4. 首版建议范围

以下为方案默认值，尚未通过性能实测：512 m × 512 m 区域、单一气候主题、1 条主河流、3 类功能分区、约 80 栋建筑体量、5 栋可进入且具有房间/楼梯/家具的样例建筑。先使用参数化建筑部件和有明确授权的少量资产，再扩充风格库。

“魔法风格”应落实为配色、材质、屋顶/塔楼规则、地标、灯光与装饰分布，以及显式的例外规则。例如浮空建筑必须声明浮空支承关系，避免验证器将所有悬空对象都视为错误。风格影响生成参数，不替代道路连通和室内可达性检查。

首版不包含完整文明模拟、多人实时共同编辑、全世界任意精度、完全自动施工图、结构安全证明、全套机电设计或从零训练通用基础模型。

## 5. 用户工作流

输入描述 → 查看世界规格与宏观草案 → 在本地查看器中检查地形和街区 → 按需细化建筑 → 移动、锁定或重生成选定内容 → 查看冲突与修复预览 → 保存新版本 → 选择导出目标及兼容配置 → 查看能力/损失报告 → 生成目标文件。

通常不在每个子步骤请求确认；只有修改会冲突于用户锁定对象、改变已有明确需求或超出预算时，才呈现具体选择。

## 6. 尚待实施阶段确定的参数

- 基准机器的 CPU、内存、GPU、操作系统及浏览器。
- Unity 与 Minecraft Java 版的具体版本、渲染管线、加载工具组合。
- 视觉参考、资产许可、首次生成等待时间和每个世界的 API 预算。
- Minecraft 是否必须直接生成独立可打开的世界目录；本方案将其列为后续专用工单。
- 工程输出的预期精度、目标工具、所在地区规范与专业复核要求；不阻塞游戏方向原型。

这些参数不会阻止当前方案设计，但必须在对应实现工单验收前固定并记录。
