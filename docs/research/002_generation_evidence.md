# 分层世界生成：证据与可行性判断

- 文档版本：0.1
- 调研日期及来源访问日期：2026-09-21
- 对应工单：[002 分层生成可行性调研](../../work_order/002_generation_research.md)
- 适用范围：个人或小团队、普通电脑、允许云端模型 API；首版目标为可编辑魔法城邦，并为 Unity 与 Minecraft 提供可导出的源数据。
- 验证方式：阅读一手论文和官方文档；未安装、运行或复现所列生成器，未执行性能测试。

## 1. 结论

**受限规模的首版具有工程可行性，完整愿景需要长期模块化建设。** 建议采用自然语言语义规划、程序化几何生成、显式约束求解、分层持久化和按需细化组成的混合系统。现有研究分别支持室内语义布局、自然场景程序化、城市道路与地块生成，但不能据此声称已有一个系统解决了从一句话到完整开放世界、双平台导出与可施工建筑成果的全部问题。

本项目中的“世界模型”首先指可编辑、可验证的世界表示及生成系统；训练预测视频或动作后果的神经世界模型是另一种研究任务，不应成为首版前置条件。这是针对用户目标与资源约束的设计判断。

## 3. 建议的生成职责分工

本节均为本项目设计建议，不表示上述论文已经实现这一组合。

| 层级 | 输入与决策 | 持久化结果 | 主要约束与验证 |
|---|---|---|---|
| 意图与规则 | 自然语言、尺寸预算、风格和目标平台能力；LLM 提出结构化草案 | 世界规格、风格词表、规则集、原始响应与解析版本 | 必填项、受支持类型、数量预算；不得直接执行模型返回的任意代码 |
| 区域地形与水系 | 区域边界、高程趋势、水源和出水口；数值算法共同决定河网与地形 | 高程块、流向/河网、湖泊、生态分区和建设适宜性 | 边界连续性、非魔法河段下游关系、湖盆与出水口；魔法例外必须显式建模 |
| 城邦与基础设施 | 主要地标、功能分区、建设适宜性；图算法与规则规划道路 | 道路/桥梁图、地块、广场、城墙和基础通行网络 | 主干连通、道路坡度、跨水连接、地块临路、建筑用地冲突 |
| 建筑 | 地块边界、用途、入口、层数、风格和体量预算 | 外壳、楼层、房间拓扑、门洞及楼梯/竖向通道占位 | 地块包含、入口接路、房间面积可行性、楼层连接；必须先预留通道 |
| 室内 | 已锁定建筑约束、房间用途、家具组合与资产包 | 家具实例、摆放关系、支撑关系、交互状态 | 碰撞、越界、门扇活动区、关键目标可达、最小操作空间 |
| 细节与表现 | 已验证的结构、材质规则、视距和细节预算 | 装饰、植被实例、派生网格与 LOD 缓存 | 不破坏结构约束；超出预算降细节并记录，不默默删掉必需对象 |

风格一致性宜通过共享的版本化风格包实现，包括比例、屋顶形式、门窗词表、材料与色板、家具组合、魔法装饰和目标平台替换规则。首版使用有限资产与规则包；开放文本出现未覆盖需求时，返回明确的占位或缺项报告，避免把任意资产生成能力当作默认能力。

## 4. 双向可行性反馈

单向“先大后小”容易在室内才发现楼梯放不下、建筑入口悬空或道路无法跨河。建议将层级组织与依赖图分开：层级表示包含关系，依赖图记录水系、道路、桥梁、地块、建筑入口之间的跨层联系。

1. 上层下发区域边界、连接点、尺寸预算、必需用途和用户锁定项；生成器先进行粗粒度可行性检查。
2. 下层生成候选，用独立校验器检查硬约束；软约束进入评分，硬约束不得用风格评分抵消。
3. 下层失败时返回 `constraint_id`、涉及实体、违反程度、失败类型和建议调整范围。超时或未找到解记录为 `unknown`，不能误记成已证明无解。
4. 优先在当前模块预算内重试或调整软条件；仍失败则向最近可修改的上层提出变更草案。例如楼梯无法布置，提议调整层数、建筑轮廓或房间数量。
5. 用户锁定项不自动删除；如果所有可选调整都冲突，则保留上个有效版本，报告未完成子树及可选调整。每轮有重试次数、计算时间与云 API 成本上限，避免无限回溯。

模块接口建议版本为 `generation_contract 0.1`：输入包含 `world_revision`、`region_id`、`coordinate_system_id`、米制单位、上下文摘要、约束、种子、资产包与算法版本、预算和锁定项；输出包含实体差异、依赖、生成状态、约束报告、资源统计和重放信息。坐标轴方向及容差由统一世界表示规范确定，模块不得自行采用平台坐标系。

## 5. 大区域与局部编辑

“大型”应由稀疏表示、按需细化和分块加载实现，不能在首帧生成全部家具。

- 宏观层先固定区域水系、交通骨架和跨块边界契约；局部块用共享边界数据及邻域上下文细化。两块独立随机生成后再拼接不能作为默认策略。
- 每栋建筑先保存外壳、用途、房间需求、入口、楼层和楼梯占位。详细家具在用户进入、主动请求或导出选区时生成；建筑“有外壳”和“室内完整”必须是不同状态。
- 渲染 LOD、语义生成完成度分别记录。只降低三角面数量不能替代尚未生成的室内语义。
- 编辑河道将相关桥梁、河岸、道路和地块标记为待重新验证，而非重新生成整张地图；编辑椅子一般只影响该房间约束和相关缓存。
- 导出前明确覆盖范围与细化级别：可以导出外壳世界，也可以等待指定建筑完成室内；不得将尚未细化的建筑描述为“完整可进入”。

首版普通电脑适配建议：本地负责轻量网格、规则、几何和存储；云模型仅处理低频语义规划与受限修改指令。完整 Infinigen 管线可作为离线资产或研究参考，不作为初版交互主循环。这一取舍来自 E7 的资源边界及本项目预算判断，具体帧率、时延和内存仍待实测。

## 6. 可重复性与生成记录

以下是设计要求，尚未得到实现验证。

- 节点种子由稳定实体 ID、世界种子、生成器版本和变体编号派生；禁止使用遍历顺序或进程随机 hash。新增建筑不应改变无关建筑的随机序列。
- 记录规范化输入、LLM 原始响应和解析结果、模型标识、资产版本及内容哈希、算法配置、依赖版本与生成输出。重新调用云模型不承诺返回相同计划；重放优先使用已保存的计划。
- 首版确定性验收限定在锁定工具链和配置下的语义/几何规范化输出。跨硬件浮点逐位一致、渲染图像逐像素一致均不是默认保证。
- 并行执行按依赖图调度，提交差异时检查基础 revision；发生冲突则重试或交接。用户编辑作为显式覆盖层或补丁持久化，并作为下一轮求解的约束。

## 7. 下一阶段的验证问题

下列是建议验收场景，全部待实现，不是现有能力报告。

| 场景 | 要证明的事项 | 必须保存的证据 |
|---|---|---|
| 一个有限区域城邦，含河流、桥梁、道路和一组建筑 | 宏观要素相容、建筑入口可达；规格允许范围内无硬约束错误 | 世界源数据、验证报告、种子、版本与查看器截图 |
| 一栋两层建筑，先外壳后室内 | 楼梯、门洞和房间连通在细化前已可行，家具不堵关键路径 | 两阶段世界差异、竖向连接图和碰撞/可达报告 |
| 移动一段河流；另做一次移动椅子 | 依赖失效范围正确，锁定项保留，更新成本随影响范围变化 | 变更集、重建清单、未受影响实体哈希 |
| 相同世界计划重放与不同块加载顺序 | 无关实体稳定、块边界一致、缓存可追溯 | 规范化输出哈希与边界比较结果 |
| 不可能的房间需求与强制求解超时 | 系统区分违反、无解证明和未知状态，有限失败并保留有效版本 | 错误分类、重试次数、资源统计和最后有效 revision |
| Unity/Minecraft 导出同一区域 | 语义特征保留到约定程度；量化后重新检查门、楼梯与通路 | 两目标导入验证及转换损失报告；由导出工单详细定义 |

下一步为统一表示与约束接口的小规模技术验证：先固定世界范围、坐标契约和资产包，再实现一个可重放的贯通样例。实现工单应由协调者编号创建；本调研不启动代码开发。
